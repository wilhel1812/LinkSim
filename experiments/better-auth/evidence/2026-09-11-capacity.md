# Durable Object capacity gate, 2026-09-11

Status: **pending**, not permission to migrate application accounts.

## Verified results

The maintainer's previous live authenticated run completed 59 requests, including
50 concurrent lookups. Matching gateway telemetry reported 0–1 ms CPU, mean
0.136 ms at whole-millisecond resolution. Sequential internal lookups averaged
57.33 ms end-to-end; the burst averaged 295.26 ms, p95 488 ms, maximum 507 ms.
Recreating Better Auth inside an existing object did not prove an object cold start.

The local workerd/D1 harness now seeds 1,000 users **and 1,000 GitHub accounts**.
All provider and Turnstile responses are mocked locally; no bulk GitHub
authorizations occur. It verifies:

- Warm session: one query, two rows read, zero writes.
- Aged-session renewal: two queries, four rows read, one write. The library's
  Set-Cookie survives the private binding; persisted expiry advances, and the
  following request performs no renewal write.
- Actual local object eviction followed by 50 concurrent requests: all succeed,
  one initialization, 122 rows read in total with the supplemental index.
- Expired and revoked sessions fail on their next request.
- Twenty simultaneous OAuth initiations succeed; each uses three queries,
  two rows read and six writes.
- A returning OAuth callback against 1,000 provider accounts originally read
  1,053 rows. A non-unique `(providerId, accountId)` index reduces this to 54
  reads, with eleven queries and eleven writes. The library still detects
  duplicate identities; the index changes no ownership or security semantics.

Run `node durable-local.mjs` after the two documented bundle commands. The
supplemental `indexes.sql` is intentionally separate from the byte-for-byte
library-generated schema. Apply it only through the validated
`node remote-setup.mjs indexes-runtime` command to the disposable D1.

## RPC lifecycle

The previous private method returned a live Response body. Cloudflare documents
that RPC contexts with outstanding stubs remain open and may be canceled when
the caller's context ends. This fits the observed complete responses followed by
canceled RPC traces, but successful HTTP alone is insufficient proof.

The method now consumes its bounded session response inside the object and
returns only status, header strings and body text. It preserves separate library
Set-Cookie headers. Local session/renewal/expiry/revocation tests pass through this
transport. Subsequent live verification at runtime version
`78062b02-eb8d-4225-a900-de57de24e00f` recorded all 59 authenticated
benchmark traces with `ok` outcomes, including 50 concurrent checks. Gateway
CPU averaged 1.407 ms, maximum 3 ms; object CPU averaged 2.661 ms, maximum
47 ms. Resolution is whole milliseconds. Normal sequential lookup latency
averaged 77.33 ms; the burst averaged 322.72 ms, p95 533 ms, maximum 552 ms.
This verifies the transport fix for this sample, not cold gateway coverage.

Source: [RPC lifecycle](https://developers.cloudflare.com/workers/runtime-apis/rpc/lifecycle/).

## Explicit daily projection, not measured account-wide acceptance

The conservative scenario is 1,000 daily active users with 30 protected API
requests and one GitHub login each. The following reserves are assumptions,
not observed staging or attack traffic; they must be replaced/validated during
rollout. Actual allowance exhaustion fails requests on the Free plan.

| Dimension | Calculation | Projected use | Free daily allowance |
|---|---|---:|---:|
| Gateway/account Worker requests | 30,000 app + 3,000 login/session + 1,000 notices + 5,000 staging + 1,000 other Workers + 5,000 abuse | 45,000 | 100,000 |
| Object requests | 30,000 app + 3,000 login/session + 5,000 staging + 5,000 abuse | 43,000 | 100,000 |
| D1 rows read | 94,557 historical app rows × 20 + 60,000 session + 56,000 OAuth + 4,000 renewal + 24,000 initialization + 100,000 staging + 100,000 abuse | 2,235,140 | 5,000,000 |
| D1 rows written | 1,035 historical app rows × 20 + 17,000 OAuth + 1,000 renewal + 1,000 public session + 2,000 staging + 5,000 abuse/cleanup | 46,700 | 100,000 |
| Object GB-s | (30,000 lookups × 0.5s + 1,000 logins × 2s + 5,000 staging × 0.5s + 5,000 abuse × 0.5s + 1,000 cold starts × 2s) × 0.128 GB | 3,072 | 13,000 |

The historical app counters are the September 10 post-hotfix 24-hour aggregate
from issue #1107, for 50 registered users. They are not a measured 1,000-DAU app
workload. This projection deliberately retains that 20× app database baseline
without claiming unmeasured savings. It assumes one active session per account;
extra devices, explicit logouts, frequent credential changes and cleanup bursts
can consume the remaining write reserve. D1 writes are the tightest estimate at
46.7%: only 3,300 additional writes fit before the approved 50% threshold.

Object duration sums per-request assumptions without discounting overlaps and
assumes the object becomes eligible for hibernation between requests. It is not
an observed billable-duration total. Pending timers/stubs must not keep it alive.

The current-activity scenario is **not yet demonstrated**: multiplying the prior
4,063 production Function requests by 20 gives 81,260/day before reductions.
SQL notice-query counts cannot safely be subtracted from HTTP request counts.
A measured post-foundations baseline must demonstrate the required reduction;
the 30-request scenario above does not substitute for this second scenario.

Sources: [DO pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/),
[Workers limits](https://developers.cloudflare.com/workers/platform/limits/),
[D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/).

## Remaining acceptance

- Confirmed cold gateway CPU (local eviction is only compatibility evidence).
- Live renewal and remaining negative provider/passkey security tests. The
  maintainer completed GitHub login/logout, passkey removal after fresh login,
  new enrollment and login with the newly enrolled passkey. Fresh-session
  rejection was observed. These checks do not replace replay/abuse tests.
- Actual billable object duration, current account-wide use, storage growth,
  persistent rate-limit cleanup and measured post-foundations request volume.
- A workload-based application write model and reserves adequate for logout,
  multi-device and signup activity before promising 1,000-user capacity.

Do not start application identity migration or remove Access while these gates
remain open. No production or shared-staging changes belong to this experiment.

## Rate-limit cleanup and accepted write-budget exception

The pinned library prunes old rate-limit timestamps when a previous key's window
resets. Against 1,000 recent limiter rows and one aged endpoint key, the local
workerd harness measured 1,007 reads and one write without the supplemental
`lastRequest` index, versus seven reads and two writes with it. The checked-in
harness now verifies indexed cleanup retains all 1,000 recent entries. The index
is non-unique; library policy, atomic counter updates and key uniqueness remain
unchanged. It adds no periodic timer or custom rate-limit implementation.

An extended local-only workload measured indexed returning OAuth initiation plus
callback at 18 writes, signup at 19, and same-origin JSON logout at five. These are
samples: first-use, repeated-IP, expired-counter and cleanup conditions affect
cost. The signup sample reused the returning login's IP. Do not treat them as
fixed upper bounds. The checked-in 20-initiation burst fixture with both indexes
measures seven initiation writes and twelve callback writes (19 total), a
different counter state from the extended sequential 18-write sample. This
variability still needs to fit the explicit maintenance/abuse reserves before
capacity acceptance; the accepted 53,700 scenario is not a proven upper bound.
The live one-tester database was 98,304 bytes with one user,
one provider account, two sessions, one passkey and ten limiter rows; its page
allocation overhead is not a per-user storage projection.

The maintainer explicitly accepted this sensitivity while keeping the **1,000-user
target**: 46,700 prior writes + 1,000 extra login writes + 1,000 extra public
session index writes + 5,000 daily logout writes = **53,700/day**. Daily logout is
an added scenario, not observed usage. The narrow exception to the 50% write
budget does not waive other quotas, maintenance reserves, migration checks or
separate production approval. The earlier table remains the historical baseline;
use the accepted sensitivity for this indexed/login-logout scenario. Avoid
counting the same cleanup work again in both measured costs and reserves.
