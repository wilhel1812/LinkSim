# R2 history prototype: storage works; maintenance must leave Pages

Scope: synthetic experiment only, based on staging c0d461b8. No application
storage configuration, auth boundary, UI, production data or retention changed.
The disposable Worker, private bucket and D1 database were deleted after the run;
the ephemeral key was removed. Measured Worker version:
`b2db163e-744f-4d12-9de7-5e9651011f18`.

All **26 measured requests returned 200**. All have a sanitized tail record matched
by path, status and timestamp within the client request interval. One separate
anonymous request returned 404. CPU below is Wrangler invocation CPU time in ms,
not network latency. No guaranteed infrastructure cold starts or burst tests were
performed. Each entropy/scenario has one sample per operation; these are observed
ranges, not statistically reliable latency distributions.

| Fixture | Archive CPU | Hydrate CPU | Restore CPU |
|---|---:|---:|---:|
| 4 KiB record | 2–3 ms | 1 ms | 1–2 ms |
| 64 KiB record | 4–6 ms | 2–3 ms | 2–3 ms |
| 256 KiB record | 11–17 ms | 5–6 ms | 5 ms |
| Maximum 20-record upload, archived as two ten-row pages | 64–70 ms/page | 4 ms/record | 4–5 ms/record |

The ten-row pages took roughly 4–5 seconds wall time (sequential storage calls).
**Reject Pages for this maintenance operation.** Successful CPU overruns are not
headroom. Hydrate/restore figures exclude application authentication, permission
queries and actual revert/save work; they do not pass the full Pages request gate.
Use a separately scoped maintenance runtime or offline administrative process;
do not put history maintenance into the authentication Durable Object implicitly.

## Storage and operation costs

For the 256 KiB fixture, snapshot plus details were **786,125 bytes** in D1.
The clear projection is **229 bytes**, excluding key/digest and SQLite/index
allocation. The complete R2 object is **805,832 bytes**, including the envelope
and JSON string escaping. This moves data; it does not compress it or guarantee
immediate shrinkage of an existing D1 file. Non-bulky rows stay inline.

Per successfully archived row, the prototype adds one R2 PUT and one GET for
verification. A later hydration adds one GET; rollback adds one GET and one D1
UPDATE. Ten-row maintenance pages used 11 D1 queries, 20 rows read, 10 written.
**The remote synthetic table has no production indexes**, so write figures are
lower bounds; fixture setup writes are excluded. Failed attempts and safe retained
orphans consume additional R2 operations/storage.

R2 Standard currently includes 10 GB-month storage, 1 million Class A operations
and 10 million Class B operations monthly; usage beyond those allowances is billed.
Source: https://developers.cloudflare.com/r2/pricing/ (checked 2026-09-17).
At one PUT/GET per row, a reserve of half the Class A allowance permits at most
500,000 successful archives/month *before* other account writes, retries and cleanup.
This is an operation allowance illustration, not a supported user count.

The earlier 80 MB production history aggregate and 20×/1.6 GB extrapolation are
not directly measured archive sizes: envelope overhead, data mix, growth,
retained originals, staging and other R2 buckets must be included. Unlimited
retained history cannot promise zero costs forever. Target remains 1,000
registered users at representative activity.

## Compatibility proved and remaining gates

Tests prove copy/verification-before-update, exact unchanged-row restoration,
concurrent single-winner archive, stale rollback refusal, ambiguous commit safety,
missing/corrupt object failure, foreign-scope rejection, mutable identity metadata
preservation, unchanged real history allowlists/denials, deletion/revocation markers
and existing revert after rollback. Local workerd/D1/R2 exercises every fixture
and checks restored strings match originals exactly.

Not yet integrated: direct archived revert, full authenticated application CPU,
real identity migration rehearsal, production-index write amplification,
archive-aware sanitized staging export, scheduled maintenance, backup-consistent
orphan cleanup and full application Manual Sync with mixed archived/inline rows.
Existing client full-upload/recovery behavior is unchanged. These gates must pass
before copying any application history or enabling an archive reader.
